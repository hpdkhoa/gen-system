A code understanding and generation engine for one 16 GB GPU

An AI model is a black box. gen-system writes down what the model assumes about your code, checks it against the parser, and compiles every line before it keeps it.

gen-system parses your code into a call graph with no model involved. For every routine it lists the inputs, the calls it makes, the data it writes and the action its name suggests. It calls each line a belief. A local model may add claims, and the parser checks every claim against those facts. You correct any line. Only lines a person verified steer generation, and the gate compiles every generated operation on its own before it enters the service. Then gen-system runs vet, build and test, and the parser rereads the result.

What the parser built · no model involved

Call graph around Checkout

Control flow of Checkout, rendered for you

Fifteen steps from a directory to this graph: walk, parse with six hand written frontends, symbol table, call edges, import graph, control flow, effect inference, standard library ingestion, then resolution. Anything a frontend cannot model becomes an unknown node with a reason, never a silent drop. gen-system draws the flowchart for a person; nothing feeds it to the model.
Three sources, and they are not equal
parser The parser derived it. Deterministic. gen-system rebuilds these on every load and never writes them to disk, so no stale cache can disagree with the code.
enrich A local model proposed it. gen-system validates it against the parser's facts before it stores it: consistent, contradicts, or needs-human.
human You corrected it. gen-system stores your value with a snapshot of what the parser derived at that moment. The only source that steers generation.

Parser beliefs come in five kinds: inputs, calls, data-change, effect, action. A model may add computation and precondition claims, which no mechanical check can confirm, so they wait for a person. When a claim says a routine saves data and the parser saw no database or file effect, gen-system marks it contradicts, attaches the reason, and never passes it to the generator.

Why the stub matters

A body that fails go build goes back to the model with the build error, at most twice. If it still fails, the gate replaces the body with return nil, errors.New("not implemented: ListOverdue") and counts the failure. So "the generated service always builds" is true and nearly worthless on its own. The number worth quoting is the stub rate: how much real logic survived the gate. The measured tables below report that number.

Then the parser rereads the output

Resolution recall over internal call edges, orphan operations (referenced but never defined), and effect sanity (a read style operation such as list or get carrying an inferred database write). Findings are unresolved, orphan, effect. With --verify-understand stop a finding halts the run; with autofix it becomes one repair round.

After the operations: go vet ./..., go build ./..., go test ./..., up to three rounds. A test failure routes the implicated service file back for repair, never the test file. The model's security review is advisory: it warns and never blocks.

The contract, and where it leaked

Every model call goes out with temperature 0.0, seed 42 and top_p 1.0. The suite sends one fixed prompt N times, hashes each answer with SHA-256, and reports distinct_outputs and dominant_ratio. It exists because a local model server does not always keep that promise: KV cache state and batch composition can move an answer. The page will not claim more than the suite measures.

The parser side is where determinism is a hard rule, and it once leaked there too. Symbol resolution picked the first match while iterating a Go map, and Go randomises map order. Two exported symbols with the same bare name could resolve differently between runs, and the call graph quietly changed shape while everything downstream looked fine. Candidates are now sorted by a stable symbol id before the tie is broken, and three tests fail against the old code (index_determinism_test.go: 50 fresh indexes of 8 same named symbols, the lowest id wins, 25 runs with the same resolved call graph).

Two contracts, one for each half: the Understand half is deterministic by construction, and its tests prove it; the Generate half pins temperature 0 and seed 42, and the suite measures how well the model server keeps that.
Why it exists

You cannot see what a model assumes about your code, so you find out when the output is wrong. That is the most expensive moment to find out.

Every AI coding tool I tried had the same shape: paste code in, get code out, read the diff, hope. I wrote three rules before I wrote any code, and gen-system follows them.

1

It must understand before it writes.

Understanding needs more than the text of the file: which functions call this one, which it calls, and what the standard library does underneath. Vector search over text chunks gives you things that look similar. This needs the call graph.

2

It must write its assumptions down, and let you fix them.

gen-system lists what it found about each routine first, as a record you can read and correct, before it generates a line. Your correction steers from then on, and if the source later changes underneath it, you see both values.

3

It must be repeatable.

Same input, same output. A result you cannot reproduce is a result you cannot trust or debug. Almost nobody builds it. The section above says exactly how far the claim goes.

The proving ground is legacy code. COBOL with copybooks and CA Gen sit next to Go, Java, TypeScript and Python. Legacy is where nobody can say what the system does and where a wrong answer costs the most.

What it is not. It is not a chat assistant, and it does not autocomplete. It does not try to be Aider, Cursor or Copilot. It refuses to ship code it cannot prove, and it shows every assumption it made on the way.

How it came to be

In 2025 I was running a legal LLM platform for a law firm. Fourteen lawyers used it every day. Nothing could leave the building, so every model ran on my own hardware: one GPU, 16 GB of VRAM.

The platform grew fast, and AI wrote a lot of the code with me. That code worked, mostly. But when I came back to a file a month later I could not tell what it assumed about the rest of the system. Neither could the AI that wrote it. I wanted a system I could argue with.

Two models need to be in memory, one to understand and one to generate, and together they do not fit in 16 GB with a useful context window. A cold load on my card is 30 to 90 seconds, so reloading on demand makes the tool unusable. What worked was sequential use with keep alive, measured, and then a sweep of quantization levels against tokens per second, VRAM and how much generated logic survives the compile gate. By datacenter standards the numbers are modest. They reproduce on hardware most people already own.

The pieces exist elsewhere. A January 2026 paper on graph RAG for codebases showed deterministic AST graphs beat both vector only and model generated graphs on Java. PRAXIS grounds generation in a dependency graph, which is the same move, but it accumulates what the model derived, where gen-system checks model claims against the parser and lets only human verified lines steer. What I could not find assembled in one place: a record of the system's assumptions that you can read and correct, model claims checked against the parser, determinism as a contract, and all of it aimed at one consumer GPU.

The experiment I still owe: feed the rendered control flow graphs back to the model as repair context, behind a flag, and measure whether it helps. I expect it does nothing for Go, because the compiler already tells the model what is wrong. It may help for COBOL and for belief enrichment, where there is no compiler to lean on. I will publish that result either way, including if it is null.

./install.sh                    # Go, Ollama, the two models, optional Postgres and Node

# beliefs land in ./your-repo/.gen/beliefs.json; correct one in the Studio or:

  -d '{"belief_id":"action:internal/loan/service.go#method:LoanService.Checkout",
       "corrected_to":"place a loan and reserve the copy",
       "human_note":"the name says checkout but it also reserves"}'

# generate a new service, gated
gen idea --out ./generated-app --verify-understand stop \
  "a library lending service with members, books and loans"

# a team's conventions, measured from a repo, checked on the way out
gen style derive ~/code/team-repo --out gen-style.json
gen idea --style gen-style.json --style-mode gate "A support ticket tracker..."
